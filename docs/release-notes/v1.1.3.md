## Theme, call sound, notifications, and a one-step unlock

Fixes the four bugs reported after testing v1.1.1 on a real device. The first two
were diagnosed by measuring rather than guessing, and one of them turned out to
be a mistake from the release that fixed it.

The only difference from v1.1.2 is the version number. v1.1.2 shipped with
`versionName "1.1.1"` still in `build.gradle`, so that APK reported itself as
1.1.1 and would have been offered 1.1.2 again, forever. This release exists to
carry the correct `versionName`.

### Dark mode only applied after relaunching the app

The app showed the correct theme on a cold start and then ignored the device
setting until the process was restarted.

`MainActivity` declares `uiMode` in `android:configChanges`, so Android does not
recreate the activity when the system theme changes - it expects the app to
handle it. React Native's `Appearance` module on Android reads the colour scheme
from **AppCompat night mode**, and AppCompat only populates that when the app
opts into its DayNight handling. Nothing did, so `Appearance` emitted one correct
value at launch and then never changed again.

One call at startup fixes it:

```kotlin
AppCompatDelegate.setDefaultNightMode(AppCompatDelegate.MODE_NIGHT_FOLLOW_SYSTEM)
```

This was confirmed with an instrumentation probe rather than inferred: the native
`appearanceChanged` event was arriving at `Appearance` and `getColorScheme()` was
correctly returning the new value, while the component using `useColorScheme()`
never re-rendered. The event was never the problem. The value feeding it was.

### Incoming calls played the dial tone

The reported symptom was that an incoming call played the outgoing dialing
sound, and that it was "completely reversed".

The channel sound pointed at `res/raw/ringtone.wav`, which had been changed in an
earlier release specifically to fix this. Measuring both files settled it: the
bundled "ringtone" and the outgoing ringback are **both a two-tone at 440 Hz and
480 Hz at equal amplitude**. That pair *is* the telephone dial tone. The earlier
fix replaced a wrong URI with a wrong asset and reproduced the exact symptom it
was meant to remove.

So the bundled clip could not be salvaged by pointing at it correctly. It was
regenerated as a real ringtone (1050 Hz + 1400 Hz under a 25 Hz tremolo, with a
two-burst envelope), which sits **100 dB down** from the dial tone at 1400 Hz.
Measured, not assumed: the new file cannot be mistaken for a dial tone.

Incoming calls now play **your device ringtone**, which is what was asked for.
The bundled clip is the fallback, for when the ringtone is set to None. That last
case is why the fallback had to be correct rather than convenient: it is precisely
the situation in which v1.1.0's original attempt left a phone silent.

One trap worth recording: notifee resolves a channel sound URI as
`contains "://"` first, then `"default"`, then a `raw` lookup. There is no string
that resolves to the ringtone stream, so the device URI is resolved explicitly
through a small native module instead of being hoped for in a string.

### The incoming-call notification survived the call

Three separate leaks, each confirmed:

- In the in-app overlay, the ringing teardown ran *after* the mutation, inside the
  same `try`. Accepting a call you are already on throws, and a declined call
  throws on any network blip. Both jumped straight to `catch` and left behind a
  high-priority, looping, non-cancellable notification.
- Draining the ring screen, or pressing back on it, cancelled nothing at all.
  Every exit that reached no JavaScript left the phone alerting.
- The ongoing-call notification had no timeout and its only cancellers were in
  React. A remote hangup while the app was backgrounded left it there permanently,
  which is the "still there for a few minutes" report.

Every exit path is now covered: accept, decline, remote cancel, server timeout,
normal end, resume reconcile, ring-screen drain, and back press. The notification
channel is the single owner of the sound, the activity plays none of its own, and
a 60-second timeout bounds the ring even if a future path is missed. The
notification can also be swiped away rather than being permanently ongoing.

### The app lock asked you to unlock twice

Clicking "Use biometrics" produced a second button, which was reported as two
steps and rightly annoying. There were two causes.

The OS prompt was raised too early to work. It needs a resumed activity, and a
cold start did not have one, so it failed and fell through to a PIN pad that sat
next to a "Use biometrics" button and a "Use biometrics instead" link. Getting
back to the fingerprint took three taps.

And the prompt could fire twice. Showing the device-credential fallback
backgrounds the app; the guard that was supposed to catch that only held while
the prompt was still in flight, so once Android dismissed the prompt the returning
app looked like a fresh excursion and the lock re-armed.

The lock is now **one step**. It waits for the app to settle, presents the prompt
itself, and drops straight to the PIN pad on any failure. The two redundant
buttons are gone, and a single prompt per lock episode is enforced by a claim
taken before the first `await`, so nothing that yields to the event loop can get
a second one. Failure messages now name the actual cause (sensor busy, nothing
enrolled, screen changed, locked out) and point at whichever control is really on
screen.

Accepting a call also no longer re-prompts. The hand-off is stamped before
navigation rather than inferred from it afterwards, closing a roughly 200 ms
window where the lock could raise a prompt over the call the user had just
answered.

A device with no biometric hardware, nothing enrolled, or a missing permission
no longer gets a dead end: the PIN pad is the floor, shown on arrival.

### Profile text was clipped

A 32-character username at 24 sp does not break, and the hero was centre-aligned,
so Android laid the text out at its own content width and ran it off the screen.
Rows also had no minimum width and fixed furniture with no shrink guard.

Every text node is now bounded by width, line count, and ellipsis mode. Usernames
ellipsise in the middle, since the first and last characters are what identify
one. The button is held at its natural size rather than being allowed to
collapse.

The page was also genuinely empty, so it now carries real data: chat, group and
unread counts, when the account was created, a call summary that says "last 50"
when that is all there is, an appearance row, and an app lock row that opens the
settings. Nothing is invented; a count that cannot be sourced truthfully is
absent rather than shown as zero.

### Also
- `AppConstants.versionNumber` had drifted to `1.0.7` and was read by nothing.
  It now matches the release and carries a comment saying it must not be treated
  as the source of truth: the installed version is read from the APK by
  `DeviceInfo.getVersion()`, which cannot drift from what was shipped.
- A dependency-free request board at `requests/index.html`. Open it in a browser,
  type requests into it, and they persist locally. No server, no build step.
- Every em dash removed from the app. 42 of them, 6 in text users read and 36 in
  comments, rewritten as sentence structure rather than swapped for hyphens.
