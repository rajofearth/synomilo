## Live theme switching, call ringtone, notification teardown, single-step unlock

Four defects fixed, each traced to a specific mechanism rather than a symptom.

### Dark mode now follows the device without a restart

`MainActivity` declares `uiMode` in `android:configChanges`, so Android does not recreate the activity on a theme change and expects the app to handle it. React Native's `Appearance` module on Android derives the colour scheme from **AppCompat night mode**, which is only populated when the app opts into AppCompat's DayNight handling. Nothing was, so `Appearance` emitted one correct value at launch and never changed again.

`AppCompatDelegate.setDefaultNightMode(MODE_NIGHT_FOLLOW_SYSTEM)` at startup restores live switching. An instrumentation probe confirmed the native `appearanceChanged` event was reaching `Appearance` and `getColorScheme()` was returning the correct value while the component never re-rendered, which isolated the fault to the value feeding the event rather than the event itself.

### Incoming calls no longer play the dial tone

The incoming channel sound pointed at `res/raw/ringtone.wav`, introduced by the release that previously addressed this. Spectral analysis showed the bundled asset and the outgoing ringback are both a two-tone at **440 Hz + 480 Hz at equal amplitude** — that pair is the telephone dial tone. The earlier fix replaced an incorrect URI with an incorrect asset and reproduced the original symptom. The clip has been regenerated as a genuine ringtone (1050 Hz + 1400 Hz under a 25 Hz tremolo with a two-burst envelope), measured 100 dB below the dial tone at 1400 Hz.

Incoming calls now use the **device ringtone**. Notifee resolves a channel sound as `contains "://"` first, then `"default"`, then a `raw` lookup, and no string resolves to the ringtone stream, so the device URI is resolved explicitly through a native call. The bundled clip is the fallback for the case where the ringtone is set to None, which is precisely the condition under which the previous attempt left a device silent.

### The incoming-call notification no longer outlives the call

Three independent leaks:

- Ringing teardown ran after the mutation, inside the same `try`. Accepting a call already in progress throws, and a rejected call throws on any network failure; both reached `catch` and left a high-priority, looping, non-cancellable notification alerting.
- Draining the ring screen, or pressing back on it, cancelled nothing. Every exit that reached no JavaScript left the device alerting.
- The ongoing-call notification had no timeout and no canceller outside React. A remote hangup while backgrounded left it permanently.

All exit paths are now covered: accept, decline, remote cancel, server timeout, normal end, resume reconcile, ring-screen drain, and back press. The notification channel is the sole owner of call sound, and a 60-second timeout bounds the ring independently of any path.

### App lock is a single step

Two causes. The OS prompt was raised before the activity was resumed, so it failed and fell through to a PIN pad flanked by a "Use biometrics" button and a "Use biometrics instead" link, making three taps to re-run a check the OS had already offered. Separately, showing the device-credential fallback backgrounds the app, which the in-flight guard did not cover, so the lock re-armed on return.

The lock now waits for the app to settle and presents the prompt itself, falling straight through to the PIN pad on any failure. One prompt per lock episode is enforced by a claim taken before the first `await`, so any caller that yields to the event loop is locked out of a second attempt. Failure copy names the actual cause — sensor busy, nothing enrolled, screen changed, locked out — and points at whichever control is actually on screen. A device with no biometric hardware, nothing enrolled, or a missing permission now shows the PIN pad on arrival instead of a dead end.

Accepting a call stamps the hand-off before navigation rather than inferring it from call-screen state afterwards, closing the window in which a prompt could open over the call being answered.

### Profile

A 32-character username at 24 sp does not break, and the hero was centre-aligned, so Android laid the text out at its own content width and ran it off the screen. Rows also lacked a minimum width and fixed furniture with no shrink guard. Every text node is now bounded by width, line count and ellipsis mode, with handles ellipsising in the middle since the first and last characters identify one.

The page also carried real data instead of being empty: chat, group and unread counts, account creation date, a call summary that states "last 50" when that is the extent of the data, an appearance row, and an app lock row linking to settings. Nothing is invented; a count that cannot be sourced truthfully is omitted rather than shown as zero.

- Every em dash removed from the app: 42 in total, 6 in user-facing copy and 36 in comments, rewritten as sentence structure rather than substituted with hyphens.
