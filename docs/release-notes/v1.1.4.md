## The camera was never permitted, the lock never armed, and a call could not survive a network change

Six bugs, all reported after testing v1.1.3 on a real device. Four of them are
regressions from v1.1.3, and two of those were caused by fixes in v1.1.3 that were
correct in isolation and wrong in combination.

Read this one if you only read one thing: **the app lock never prompted, because I
broke it in v1.1.3.** Everything else is a bug found and fixed.

### The app lock never asked for biometrics, though Settings said it was on

**The cause was mine.** v1.1.3 added a five second "call hand-off" stamp so that
accepting a call would not re-prompt you for a fingerprint you had already given.
I also stamped that timer inside the `AppState` listener that runs on **every**
return to the foreground. So opening the app normally stamped a call hand-off, the
lock read it as "the user just answered a call", and suppressed the prompt.

The stamp belongs at the one place a call is actually navigated to. It now does
and only does. The regression is covered by a test that fails against the released
build.

The same rewrite left five smaller faults, all fixed:

- `prompting` could stay set after the OS dismissed the prompt, so the screen
  waited for a fingerprint that no longer existed.
- A memoised handler captured the first lock episode forever, so a second lock
  could never claim its own prompt.
- A ref-backed foreground flag could not re-trigger the prompt effect.
- The lock exemption for an accepted call had no deadline, so a failed navigation
  would have left an install permanently exempt from asking.
- Settings and the lock screen could describe the lock differently: one said
  "not available" where the other said "off", and both could promise a PIN
  fallback that was not on screen. There is now one function that decides what the
  lock will actually do, and both rows read it.

One claim in the previous release's notes was wrong and is retracted: biometric
re-enrolment does **not** invalidate this app's secure store. It holds no key bound
to a biometric, because it passes no `CryptoObject`. A keystore loss surfaces as a
reset control, which is recoverable, not silent.

### Video calls had no camera at all

The picture in picture box was empty because **`android.permission.CAMERA` was
never declared in the manifest.**

`react-native-webrtc` does not declare it on your behalf. Android denies an
undeclared permission with no dialog and no log, so the request came back
"denied", `getUserMedia` deleted the video constraints, and **no camera track was
ever created**. The preview box still mounted, because a stream id is returned for
an audio-only stream too, so it rendered permanently empty with no error anywhere.

Outgoing video was broken for the same reason. This was never a WebRTC bug.

The call screen now logs every local track with its `readyState`, so the two
outcomes are distinguishable on a device, and the preview says "No camera" instead
of being blank.

### A call died every time the network changed

Your report that calls are not smooth had one dominant cause. The screen armed a
25 second deadline when the call was answered and **never re-armed it**. Any call
that blipped afterwards was hung up by a clock armed when it started. There was
also no way to ask for a fresh path: no `restartIce`, and `react-native-webrtc`
gathers candidates once and never again.

So a Wi-Fi to LTE handover, a lift, or a tunnel killed the call, or left you
watching "Reconnecting" with nothing being done about it.

The deadline now belongs to the phase it expires. A call that was connected has no
clock running at all, so it cannot be torn down by an old one. Recovery is real:
a native `ConnectivityManager` watcher detects the network changing under a live
call and asks for an ICE restart, and ICE failure triggers the same recovery
instead of ending the call. Recovery is bounded at two attempts and a shared
window, and the peer is told the call ended exactly once, only after recovery is
genuinely spent.

You now see a real difference between "connecting", "reconnecting" and "failed",
and a call that never connects ends after 25 seconds instead of ringing forever.

### The ringtone stopped the moment you opened the app

v1.1.3 fixed one real problem, the notification outliving the call, and created
this one. It made the notification channel the only thing in the app allowed to
make a ringing sound, everywhere. But the in-app call screen has no ringing of its
own, so foregrounding a call cancelled the notification and with it the only sound
the app had.

Sound is now owned by whatever is actually on screen: the in-app overlay rings
while the app is visible, the notification channel rings while it is not, and
control is handed over in both directions without a gap.

Two more causes of "sometimes there is no ringtone" are fixed:

- The device ringtone was accepted if it merely looked valid. A ringtone from a
  cloud provider or a revoked default resolved to something Android could not
  open, and the channel is immutable once created, so the phone stayed silent
  forever. It is now checked for actual playability before being used.
- Leaving a call reset the audio mode unconditionally, which on many devices mutes
  the ringer for the **next** incoming call. Audio is now released only by the
  thing that took it.

### Audio stopped when you came back to the app mid-call

Returning to the foreground ran the same release path as ending a call, so a live
call dropped out of voice-call mode. A live call keeps its route now.

Bluetooth headsets were also ignored for the entire call, because the earpiece was
forced at setup. A connected headset or wired device is preferred, earpiece is the
fallback, and the in-call speaker toggle is unchanged.

Also in the queue: ICE candidates that arrived before the remote description were
never flushed on the answering side, and Convex deletes consumed signals, so they
were never retried. That was your "sometimes it connects, sometimes it does not".

### Talking time said 275 hours

That number was real arithmetic on a lie, and it can be shown exactly.

One call row had `createdAt` 11 days before its `endedAt`. It had been left
"active" by a killed app, and the cleanup sweep that eventually closed it wrote
**the time it noticed** as the end of the call. Eleven days of a row nobody was
ever on the phone for became eleven days of "talking time".

The fix was written but **never deployed**, which is why you still saw it. Talking
time is now only counted for a call that was answered and then hung up within the
window a conversation can physically last, so a record whose end was never observed
contributes nothing. It is deliberately "unknown" rather than zero.

**Your real total across those 50 calls is 76 seconds.** Verified against the live
backend after deploying.

### Not fixed, and it needs your decision

**Calls have no TURN relay.** They are STUN only, so on symmetric NATs and networks
that block UDP a call cannot connect at all. Fixing it needs a TURN account or a
self-hosted `coturn` VM and a shared secret, which is your call to make. The exact
steps are written up in the backlog. TURN raises the chance a call connects; it
does nothing for a call that connects and is then dropped, which is why the
deadline and ICE restart work shipped first.

One crash remains unfixed: accepting a call from the foreground still crashes, and
I could not reproduce a throw for it. What was fixed removes the one path that
structurally could produce it, since foreground accept was the only accept path
that bypassed the single guarded entry point and could open two call screens. If
it still crashes, the red box in the app is an error boundary, and the line beneath
it names the component that threw.
